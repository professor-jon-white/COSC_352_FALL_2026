## Concurrency Analysis

- `ingest.go:150-170` — `fetch`: two goroutines download the two sources with `context.WithCancel` so either failure cancels the other; `sync.WaitGroup`.
- `main.go:60-70` — two goroutines decode the two JSON files concurrently.
- `analysis.go:36-61` — crime aggregation worker pool: `jobs` channel bounded at `2*workers`, N workers each with a private `Result` (maps), `partials` channel (cap `workers`), a feeder goroutine that closes `jobs`, waits, closes `partials`; reducer merges on the main goroutine. `linked`/`firstArrest` maps are built before the pool starts and only read inside it (`analysis.go:12-33`) — correct, race-clean.
- **Not concurrent:** the arrest pre-pass (`analysis.go:15-33`), the `CategoryByNeighborhood`/`WeaponByNeighborhood` cross-tabs (`analysis.go:84-92`) and the incident index (`analysis.go:93-118`) all iterate `crimes`/`arrests` again sequentially — the README admits this. Real concurrency in one aggregation stage plus I/O; parallel join is partial.

## Memory/Resource Analysis

- README has a complexity/memory paragraph (O(C+A+W·G+K), bounded channel limits queued work not storage, GC owns heap, advice for memory-constrained machines); `runtime.ReadMemStats` printed at the end; `io.LimitReader(…, 64<<20)` guards downloads; HTTP timeouts; manifest/rows consistency check prevents analyzing a half-written snapshot.
- Weak points: rows are `map[string]any` (every attribute boxed), both JSON files are decoded fully into memory, and `crimes` is iterated four separate times. 98 MB RSS for 11.7 MB of JSON. Some real thought, not a lean design.

## Architecture & Code Quality

Single `package main`, but files map to pipeline stages (ingest → normalize → analysis → report) and the README names this as a Pipeline, which is fair. Strengths: provenance manifest, refusal to overwrite an existing snapshot, pagination with duplicate-ID detection, schema checks, deterministic tie-breaking, `time/tzdata` embedding, tests with `httptest`. Weaknesses: `Row map[string]any` loses all typing; `Result` is a grab-bag struct with a 120-character field line; `report.go` is one 150-line function; terse one-letter variable names (`a, b, e, ea, eb`); the `if *mode == "analyze" {} else if ...` empty branch (`main.go:38`). No Builder/Strategy/Factory. README is long and careful and matches the code — the opposite of boilerplate; if anything it over-caveats.

## Stakeholder Questions & Value Assessment

All five questions join the two datasets (by neighborhood or by month) and each states a purpose ("for citywide coordination", "for staffing review", "for investigative resource planning", "for violence-prevention program planning"), but **no municipal office is actually named** — a Mayor's Office / BPD / City Planning reader is implied, not addressed. The joins are meaningful aggregate joins, not coincidental counting, and the report is admirably honest that 69% of arrests lack a neighborhood, which materially limits Q1, Q3, Q4 and Q5. Q4 (Downtown has 3.6% of crime but 8.3% of geocoded arrests) is the one finding a leader would act on; Q2 is a plain monthly count; Q3/Q5 are mix comparisons with small differences. Visualization is thin: Markdown tables plus one signed ASCII bar chart. Useful, cautious, but not deeply insightful.

- Only one ASCII chart; otherwise tables.
- 69% of arrest rows lack a neighborhood, so four of five answers describe a 31% subset (disclosed).
