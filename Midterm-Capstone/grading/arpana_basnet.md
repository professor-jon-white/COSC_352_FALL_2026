## Concurrency Analysis

- `service_data.go:168-172` — 311 ingestion: single `csv.Reader` goroutine feeds `jobs := make(chan ServiceJob, 256)`; 4 `serviceWorker` goroutines (`:66-139`) each own a private `map[string]ServiceMetrics`, parse dates/status and aggregate; results returned on a `chan ServiceData` and merged by the reader goroutine (`:225-237`). Correct fan-out/fan-in with no shared mutable state.
- `main.go:73-114` — identical pattern for the notice file (`countWorker`, 4 workers, buffered channel 256).
- `main.go:166-172` — both datasets are loaded concurrently (`go loadRequestCounts`, `go loadDataset`).
- `service_data.go:34-44` — `sync.Once` guards the 311 summary so Q3–Q5 reuse one load.
- `join.go:5-48` — `matchNeighborhoods`: 4 goroutines + `sync.WaitGroup` do a set-intersection over ~290 names. Technically correct but token (the work is microseconds).
- Q2–Q5 analyses (`analysis.go`, `dumping.go`, `backlog.go`, `closure.go`) run sequentially on the main goroutine.
- CSV tokenization itself is sequential per file (acknowledged in README). Race detector clean. **Level: partial-to-full** — parallel per-row processing/aggregation with worker pools on both files, but the join/analysis stages are not meaningfully parallel.

## Memory/Resource Analysis

Strong. Streaming `csv.Reader` (never `ReadAll`), bounded channels (256) give back-pressure, workers retain only per-neighborhood summary structs (never raw rows), `strings.Clone` on new map keys (`service_data.go:128`, `main.go:38`) to avoid pinning CSV line backing arrays, fixed worker count, `defer file.Close()`, workers always drained even on read error (`service_data.go:224`). Result: 13.4 MB peak RSS for a 380 MB input — the lowest of the four submissions. The README's "Memory and resource management" section accurately describes what the code does. No `runtime.MemStats` reporting.

## Architecture & Code Quality

- Single `main` package of 7 files; separation is by file (ingestion in `service_data.go`/`main.go`, join in `join.go`, one file per question). Reasonable for the size but no packages, no interfaces, no tests.
- No named design pattern is claimed or realized; the structure is a de facto pipeline + worker pool. Question dispatch is hard-wired inside `reportTopNotices` (`analysis.go:49-62`), which also calls `os.Exit` — Q1's function is doing orchestration.
- The `visualize` program re-parses the human-readable `results.txt` with string prefix matching (`visualize/main.go:56-141`) to build charts. This is fragile coupling (any change to a `Printf` label breaks the report) — the engine should emit structured data (JSON) for the renderer.
- Code is clean, idiomatic, consistently formatted, with sensible error handling and honest data-quality counters (missing dates, negative durations, duplicate statuses). README is thorough and candid about limitations.
- Originality: the README's limitations/analysis-definitions sections are detailed and match the code precisely; nothing reads as boilerplate that the code does not back up.

## Issues

1. No unit tests and no run script; `go.mod` requires Go 1.27.2 (triggers a toolchain download).
2. Join stage (`join.go`) is token concurrency over ~290 strings; Q2–Q5 analyses are sequential.
3. `visualize` scrapes the text output of the engine instead of consuming structured data — brittle.
4. Q5 uses means on a heavy-tailed distribution; Q4/Q5 use a two-bucket split rather than per-neighborhood analysis.
5. No design pattern named or realized; flat `main` package; question orchestration buried in Q1's function.
